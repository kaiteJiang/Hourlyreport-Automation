# v2026.7.28.115 发布与 README 重构设计

## 背景

当前 `main` 已完成商务通本地 API 启动与日报读取性能优化，但尚未形成新的正式版本。
现有 README 信息完整，却把产品介绍、业务口径、开发命令、工程结构和版本历史连续
堆叠在同一主线中；首屏徽章和导航密度较高，用户需要阅读较长内容才能找到安装与
日常操作入口。

本次发布把性能优化正式纳入 `2026.7.28.115`，同时将 README 重构为面向同事和
新用户的产品首页。开发与维护信息继续保留，但后置并折叠，不与用户主线争夺注意力。

## 目标

1. 发布正式版本 `2026.7.28.115`，累计序号由 `114` 永久递增为 `115`。
2. 重构 README 的信息架构、视觉层级和文案，使其更像克制、可靠的企业级产品首页。
3. 生成新的桌面主程序、在线更新包和完整安装器。
4. 验证在线更新包不会覆盖用户配置和运行数据，所有发布产物不包含真实凭据。
5. 提交本次源码、文档和发布元数据并推送 `main`；GitHub Release 由用户手动创建。

## 非目标

- 不修改日报、小时报、百度 API、商务通统计或 Excel 写入业务逻辑。
- 不新增图片生成、宣传视频、外部网站或新的安装流程。
- 不自动创建 GitHub Release，不上传 Release Assets。
- 不提交本机项目配置、真实授权文件、日志、报告、备份或业务数据。

## README 受众与内容主线

### 主要受众

README 首先服务第一次接触产品的同事、安装维护者和新用户。开发者仍能在同一文档
中找到命令、工程结构和协作规则，但这些内容位于用户主线之后。

### 视觉方向

- 延续现有蓝绿科技风、产品横幅、GUI 截图和品牌图标。
- 首屏只保留产品名、一句话价值、四个关键能力徽章和精简导航。
- 使用短段落、留白、四列能力卡和清晰表格替代连续大段说明。
- 文案强调“本地优先、API 优先、Excel 安全、失败可控”，不使用无法验证的营销词。
- 不新增远程图片依赖，不生成新的视觉资产。

### 信息架构

README 按以下顺序重排：

1. **Hero 首屏**：品牌横幅、产品名、核心价值、版本/平台/本地优先/Excel 安全徽章。
2. **产品一览**：GUI 截图、四张能力卡和一段产品定位。
3. **从数据到报表**：用单个主流程图解释百度、商务通、合并、备份、写入和复核。
4. **核心能力**：用精简表格说明百度、商务通、小时报、日报、多项目与在线更新。
5. **快速开始**：完整安装器、GUI 日常操作和 HERMES 固定入口。
6. **可靠性与安全**：集中呈现 Excel 边界、凭据保护和失败处理。
7. **发布与更新**：突出当前版本、Release Tag、在线更新包和完整安装器。
8. **深入了解**：折叠业务口径、数据模式、开发命令、工程结构和协作规则。
9. **版本历史**：主线只显示最近版本，完整历史链接到 `docs/releases/`。

重复的产品定位、Token 安全说明、发布规则和开发者提示合并到唯一位置。多项目架构
不再单独占用一整段主线图，而在核心能力和折叠技术说明中保留。

## v2026.7.28.115 发布内容

中文发布说明突出以下变化：

- 商务通本地 API 未就绪探测由 15 秒缩短为 5 秒。
- 同一登录身份可从历史日志恢复接口 URL，但公共查询参数、请求头和 Token 仍只使用
  当天材料；当天认证不完整时保持未就绪。
- 13 条会话以最多四路并发读取，单会话仍严格执行
  `visitor_info → visitor_card`。
- 任一会话失败时整批失败且不缓存部分结果，项目快商通指标继续按既有规则处理。
- 脱敏测量中 26 次请求峰值并发为 4，正常采集约 1.96 秒；外部网络或上游服务仍可能
  产生偶发长尾。
- KST 管理器测试夹具改为真实服务器生命周期语义，完整测试集达到 787 项通过。
- README 完成面向用户的信息架构与视觉层级升级。

发布说明不声称能够完全消除网络长尾，也不把测试夹具修复描述为生产故障修复。

版本号固定为 `2026.7.28.115`，Tag 为 `v2026.7.28.115`。

## 构建与产物

构建顺序：

1. 重新构建 `hourlyreport_automation.exe`。
2. 生成在线更新包
   `Hourlyreport_automation_v2026.7.28.115.zip`。
3. 生成完整安装器
   `Hourlyreport_automation_setup_v2026.7.28.115.exe`。
4. 清理发布输出，仅在 `dist/` 保留上述两个最终发布包；桌面主程序不留在 `dist/`。

必须消除或解释现有构建测试中的
`Duplicate name: 'hourlyreport_automation.exe'` 警告。发布清单中同一路径只能出现
一次，不允许通过忽略警告完成发布。

## 更新包覆盖规则

在线更新包不得包含或覆盖：

- `configs/`
- `secrets/`
- `logs/`
- `reports/`
- `backups/`
- `diagnostics/`
- `kst_exports/`
- `browser_profile/`
- `runtime/`

完整安装器可以包含默认项目配置，但不得包含真实 `secrets/secrets.json`、
`.baidu-secrets`、OAuth Token、HMAC 密钥、本机日志、报告、备份、诊断包或快商通
导出数据。

## 验证

发布前必须完成：

1. README 链接、锚点、版本号和产物名称检查。
2. 版本与更新器相关专项测试。
3. 构建和发布包专项测试。
4. 完整 `pytest`。
5. 在线更新包 ZIP 清单审计，确认排除目录和敏感文件不存在，且主程序只有一份。
6. 完整安装器内容或构建清单审计。
7. 使用更新器逻辑验证 `v2026.7.28.115` 格式可识别；不依赖尚未创建的远端 Release。
8. `git diff --check`、敏感模式检索和提交范围检查。

不运行真实 `run` / `run-daily`，不写目标 Excel。

## Git 与交付

- 在隔离工作树和 `codex/release-2026.7.28.115` 分支实施。
- 用户现有配置和 `docs/releases/2026.7.22.109.md` 本机修改不得进入提交。
- 通过任务审查与最终审查后合并回本地 `main`。
- 推送 `main` 到 `origin`，不创建 Pull Request。
- 不创建 GitHub Release；向用户交付两个发布包路径、提交哈希、建议 Tag 和中文发布说明。

## 失败处理

- 构建、测试、包审计或更新器识别任一失败时停止发布，不推送未经验证的提交。
- 若完整安装器工具不可用，保留已验证源码和在线更新包，明确报告阻塞，不伪造安装器。
- 若远端 `main` 在推送前已前进，先检查差异；禁止强推。
- 若发布输出包含敏感文件或重复主程序，删除有问题的产物并修复构建逻辑后重新生成。
