# KST 本地 API 性能优化设计

## 目标

在不改变自动推送白名单、推广 ID 项目映射和小时报/日报统计口径的前提下，消除 GUI 运行期间的周期性卡顿，并显著缩短重复查询商务通数据的时间。

## 已确认的瓶颈

- GUI 当前每 15 秒完整刷新身份注册表。
- 两个已登录身份共有约 384 MB 日志；一次完整日志解析约 3.9 秒。
- 昆明牛单次报表请求会重新解析日志、读取四个数据库并逐条请求会话详情，实测耗时 8.25～11.24 秒。
- `KstConversationService` 虽有会话缓存，但注册表每次请求都创建新运行时，缓存无法跨请求复用。

## 方案选择

采用分层、自动失效的内存缓存：

1. GUI 每 15 秒保留轻量健康检查；拥有本地服务且状态正常时，完整身份刷新改为每 5 分钟一次。服务未就绪时仍每 15 秒重试，确保新登录身份可以自动恢复。
2. 日志解析器缓存每个文件的读取偏移和已解析结果。文件只追加时仅读取新增字节；文件被删除、截断或轮转时安全地完整重建。
3. 身份注册表按“项目 + 日期”复用运行时。缓存以自动来源集合、数据库文件状态和最长 60 秒有效期共同控制；任一条件变化即重建。

不采用长期固定结果缓存，也不把所有本地数据库记录直接视为自动来源。

## 数据流

1. GUI 启动时发现本地商务通身份并完成一次注册表刷新。
2. 日志缓存首次建立完整快照；后续调用只消费追加内容。
3. 报表请求先取得最新日志快照。
4. 若自动来源集合未变化、数据库状态未变化且运行时未超过 60 秒，则复用现有服务及其会话详情缓存。
5. 若发现新自动推送、数据库变化或超时，则重建运行时；仍只选择自动推送白名单中的会话。

## 缓存失效与异常处理

- 日志文件缩小、消失或轮转：丢弃该目录缓存并完整重建。
- 商务通身份、安装目录或数据库路径变化：身份缓存键变化，自动建立新缓存。
- 服务未就绪：不执行 5 分钟降频，继续每 15 秒完整重试。
- 运行时构建失败：不覆盖最后一次成功缓存，也不缓存零值或失败结果。
- 缓存仅驻留当前 GUI 进程内，退出程序后自动清空。

## 并发与安全

- 日志缓存和运行时缓存使用锁保护，避免 API 线程并发请求重复构建或读到半成品。
- 缓存只保存本地业务对象，不写入凭据、Token、日志或新的持久文件。
- HTTP 接口、端口、认证方式及响应结构保持不变。

## 验收标准

- 原“一个 `msgType=48` 批次包含多个会话 ID”的测试继续通过。
- 人工历史查询响应仍不进入自动来源白名单。
- 日志无轮转时，第二次解析只读取新增内容。
- 健康状态正常时，15 秒定时器不再每次完整刷新注册表。
- 同一项目、日期且数据未变化时复用运行时；数据库或自动来源变化时重建。
- KST 全套测试通过，昆明牛成品 API 总数继续与人工查询一致。
- 重复请求耗时相较当前 8.25～11.24 秒明显下降，GUI 后台不再周期性扫描全部日志。
